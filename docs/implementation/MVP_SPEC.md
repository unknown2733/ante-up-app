# 테스트넷 MVP 구현 명세

## 0. 문서 상태와 사용법

확정된 제품 결정을 구현 단위로 연결한 v0.1 명세다. 기존 논의/결정 문서를 옮기거나 대체하지 않는다. 경제 규칙의 근거는 연결한 결정이며 과거 문서의 당시 '미정' 표현은 해당 범위의 후속 결정과 함께 읽는다. 이 문서의 화면 경로·모듈명·필드·실행 순서는 **구현 초안**이다. 실제 코드베이스와 SDK/계정 제한을 확인한 뒤 구체화한다. 새 권리·요율·자동 공개 범위를 기술 선택으로 추가하지 않는다.

이번 산출물은 명세이며 코드·유료 호출·서버 접속·배포·지갑 지급은 수행하지 않았다. 현재 외부 코드 작업공간은 HOME의 ante-up 저장소를 따른다. 구현 시작 시 기존 코드와 AGENTS를 먼저 확인하고 이미 있는 구조를 재사용한다.

화면 경로/탭 구성은 초안이다. 읽기 전용 공개 프로필/검증은 지갑 연결 없이 읽을 수 있게 제안한다. 사용자 상태 변경은 지갑 서명으로 본인을 확인한다. 모드 이동만으로 기록 종료·토큰 매매·담보 전환하지 않는다. 공개 프로필 노출을 무료 선택 화면에서 알린다.

핵심 표시 원칙: `내 선택 이후 지표 변화`, `이번 주 가격 변화`, `내 거래 순손익`을 구분한다. 금전 거래도 tUSD의 시험 결과임을 표시한다. 데이터 미관측은 0%, 증명 대기는 실패, 평가액은 즉시 출금액으로 바꾸지 않는다.

## 5. 계산·가격·자본 규칙

### 5.1 데이터와 가격

1분 발생 건수→일 환산 활동률→반감기3일 EWMA S→7일 전 S와 비교한다. 기본28일 이력의 가장 오래된 하루 평균으로 초기화하고 나머지27일을 재생한다. 결측을 0으로 넣지 않는다. 다음 정기 관측의 정상 연결까지 준비 확인한다. 정확한 구문/제한된 별칭 OR·영어·리포스트 제외 등 [Counts 정책](<./sources/2026-10-11 영어 키워드 Counts 집계 규칙 채택.md>)을 적용하며 실제 API 매칭은 별도 확인한다.

```text
r(t) = S(t) / S(t-7일)
h(t) = min(r(t), 5)
c = P_G / r_G          # 정상 졸업 시 0 < r_G < 5
P(t) = c * h(t)
Pmax = 5 * c            # 주간·진입·정정 때 재설정하지 않음
무료 성과 = h_exit / h_entry - 1
```

무료 성과는 졸업 전 커브 가격과 별개다. 주간 표현은 같은 스냅샷의 B_w/h_w를 저장해 P=B_w*h/h_w로 이어지고 완료 거래를 소급 수정하지 않는다. 상한 전 r은 보조 정보로 보존한다. [가격 결정](<./sources/2026-10-12 EWMA 가격 연결과 고정 상한 채택.md>)이 정본이다.

### 5.2 커브·졸업

표준 SPL 키워드 토큰2000개, 커브1000/볼트 재고1000. tUSD는 소수6자리 시험 결제자산이다.

```text
p(q) = 1 + 0.2*q/1000
R(q) = q + 0.0001*q*q   # q는 순판매량, 0..1000
매매 총대금 = 해당 두 R 값 차이
```

등록10 tUSD, 커브 거래0.1%, 시장80/프로토콜20. 순판매1000·판매준비금1100, 지표 준비·양쪽 활동률100 이상·0<r_G<5·실제 자금/예산·담보를 검사한다. 미충족 시 상단 매수 제한·매도/여유분 재매수를 허용한다. 마지막 매수와 졸업은 별도 거래다. 졸업은 초기 출연·자산/재고 이전·고정 c/Pmax·초기 잠금 지분·현물/LP 개방을 원자적으로 처리한다.

고정 지원5시장, 시장별 최초 출연 상한10000/총50000 tUSD, 버퍼500, 졸업 목표 가용3000. 자금 생성 능력이나 미이전 예산은 자산이 아니다. 초기 LP 연속15분 뒤 조건을 만족하면 Pro 개방. 초기 토큰 보유권과 같은 mint를 유지한다. 근거: [커브](<./sources/2026-10-12 자체 커브와 초기 가격 물량 졸업 기준 채택.md>), [비용/버퍼](<./sources/2026-10-12 커브 비용 등록비 출연 한도와 버퍼 채택.md>), [지원](<./sources/2026-10-12 키워드 중복 처리와 첫5개 데이터 자본 공동 지원 채택.md>), [전환](<./sources/2026-10-12 원자적 졸업과 최초 LP15분 후 Pro 개방 채택.md>).

### 5.3 현물·Pro·예약·LP

```text
현물 매도 대금 = q*P - 거래 수수료
N = C*L; d = +1(롱), -1(숏)
Pro 총지급 = max(0, C + d*N*(P/P0 - 1))
M_long = C + N*(Pmax/P0 - 1); M_short = C + N
Rs = Q*Pmax; Rp = 열린 포지션의 M 합
가용 F = A - Rs - Rp - H - B
LP 처리 시 NAV E = A - Q*P - D
LP 지분가격 = E / 총지분
```

P0는 유효한 양수이며 L<=5. A는 수취한 담보 포함 실제 결제자산, H는 환급 가능 선납·외부 귀속·확정 미지급 의무, D는 해당 NAV 부채다. 동일 의무를 중복 차감하지 않는다. 자기 토큰 표시가·미래 비용 수입을 자산에 더하지 않는다. 롱숏 예약 상계는 없다.

신규 현물 판매/Pro와 LP 출금은 실행 후 F>=0을 검사한다. 기존 종료는 그 계약 예약으로 지급한다. 평가액0이더라도 기간 내 회복 가능 포지션의 최대 예약을 유지한다. 미지급 정산금은 Claim으로 옮겨 지급 전까지 부채/예약에 남긴다. Q는 외부 환매 대상 수량으로 지갑 전송만으로 감소하지 않는다.

LP는 Pro 지급액 전부 확정 및 유효 NAV가 있을 때 정해진 구간에서만 발급/상환한다. 초기 잠금 지분과 외부 LP는 동순위 비례 손익, 출금은 요청 전액 가능할 때만 처리한다. 초기 잠금 지분 일반 출금 금지. 근거: [지급](<./sources/2026-10-12 테스트넷 최대 지급 담보와 가격 비청산 채택.md>), [예약](<./sources/2026-10-12 통합 예약 장부와 거래 출금 한도 채택.md>), [LP N3/L1](<./sources/2026-10-12 LP 지급 확정 시점 평가와 동순위 손익 채택.md>).

### 5.4 비용과 시간

## 8. API·프로그램 액션 초안

읽기 API는 시장/관측, 내 기록, 공개 무료 프로필, 순위, 기록/증명, 내 Pro/LP, 거래 견적을 제공한다. 공개 응답 DTO에 개인 Pro/LP 금액을 섞지 않는다. 앱에서 숨기는 것을 온체인 비공개로 설명하지 않는다.

쓰기 액션은 `registerMarket`, `curveBuy/Sell`, `graduate`, `spotBuy/Sell`, `open/closeFree`, `open/closePro`, `finalizeEpoch`, `claim`, `deposit/withdrawLP`, `publishSnapshot`, `linkProof`, `requestFaucet`, 운영 상태 변경으로 나눈다. 실제 명칭/프로그램 분할은 초안이다.

견적에는 market/phase·수량/담보/방향·게시/설정 버전·평가 시각·만료·총납부/최소수령·수수료·만기·예상 예약을 포함하는 안을 제안한다. 사용자 승인한 가격/납부 경계를 넘으면 실패/재견적한다. 견적은 자본 선점이 아니며 온체인 실행 시 담보·데이터 나이·시간·잔고를 다시 검사한다. 구체 TTL/슬리피지 기본값은 별도 기술 명세에서 닫는다.

중복 제출에는 동일 요청/서명/기록 버전을 조회하고, 타임아웃만으로 새 지급 트랜잭션을 만들지 않는다. API 한도만 적용하면 온체인 직접 호출로 신규 무료 제한을 우회할 수 있으므로 한도 강제 경로를 프로그램 또는 검증 가능한 진입 승인으로 설계한다. 구체 채택은 코드 계정 경합/실행 한도 검토 후 결정한다.

## 9. 운영자·faucet·비용·배포

운영자가 시장 지원·게시·중단/재개·졸업/정산 작업·출연·faucet·증명 복구·설정 변경을 통제하는 방향으로 권한표를 작성한다. 사용자 서명과 운영자 서명을 구분하고 게시 키/SAS 키 분리를 유지한다. 업그레이드/설정 권한은 액션·이전값/새값·적용 버전·기존 계약 영향으로 명시한다. 기존 공개 졸업 호출 허용 결정과 운영자 중심 운영은 병존 가능하므로 운영자가 실행한다는 이유만으로 permissionless 요청 경로를 임의 삭제하지 않는다.

faucet은 tUSD와 거래에 필요한 Devnet SOL 문제를 앱 안에서 해결해야 한다. 소액 SOL 동시 지급을 구현 후보로 두고 지급량/재지급 주기/전체 한도와 SOL 대납 대안은 배포 전 정한다. 키워드 토큰 발행 권한 제거와 tUSD 발급 역할을 구분한다.

비용: X UTC 하루$10/초기$100, 초기 총$150. 무료 동시3/시장1, 신규 지갑6·전체100/이동24시간, 미완료 의무200. 임시 사용량+수용 의무의 예상 저장량80%에서 신규 제한. 기존 종료/보관/발급 의무를 일일 신규 제한으로 막지 않는다. 프런트 조회는 공통 캐시를 사용한다. [비용 제한](<./sources/2026-10-12 MVP 수집과 무료 기록 비용 제한 채택.md>).

홈서버 우선, 제품 로직/배포 설정 분리, 영속 DB·원자료·작업 상태 백업 및 재시작 복구. 서버 이전 시 중복 워커를 방지한다. API 키·체인 키는 저장소/클라이언트에 노출하지 않는다. 실제 호스트 사양·접속·백업 위치·지속 운영 예산은 배포 전 정한다.

앞 단계는 뒤 단계 완료를 뜻하지 않는다. 전체 MVP에서 금전/Pro/LP가 제외된 것이 아니다. 각 단계의 계약을 닫으면 해당 모듈 구현을 시작할 수 있다. 권리/요율/공개 범위를 바꾸는 발견은 새 결정으로 다루고, 구현 디테일은 명세에 근거와 테스트로 남긴다. 위 표는 작업 의존성 설명이며 Hermes Task의 실행 상태 정본을 대신하지 않는다. 작업 발행·일정 등록은 이번 요청에서 수행하지 않았다.

## 12. 작업 분할과 통합 계획

2026-10-12 사용자 요청 “각 부분별로 어떻게 나눠서 작업을 구현하고 합칠 수 있을지 계획해봐”에 따른 구현 계획 초안이다. 새 제품 결정·작업자 배정·스레드 생성·배포를 실행한 것은 아니다. 아래 담당은 역할이며 실제 사람/에이전트가 지정된 상태가 아니다. 코드 저장소 구조를 아직 확인하지 않았으므로 소유 경로는 논리적 구분이다. 별도 서비스/저장소 7개를 만드는 계획으로 해석하지 않는다.

### 12.1 분할 원칙

- 먼저 공통 계약과 재현 가능한 예제를 맞춘 뒤 데이터·조회·화면을 병렬 진행한다. 각 계층이 상태명·단위·계산식을 독자적으로 정의하지 않는다.
- 자산을 변경하는 커브→졸업→현물→Pro→LP는 하나의 회계 담당이 통합 책임을 맡고 순차 확장한다. 계산 보조 작업은 분담 가능하나 공통 볼트 계정/예약 장부에 대한 병렬 수정은 피한다.
- 데이터가 만든 가격 후보와 체인에 실제 게시된 거래용 스냅샷을 구분한다. 화면은 후보를 체결 가능한 가격처럼 쓰지 않는다.
- 매 통합 단계마다 실제 사용자 행동을 한 번 완주한다. 모의 응답으로 화면이 동작하는 것과 체인/외부 서비스 연동이 동작하는 것을 별도로 보고한다.
- 홈서버 배포는 제품 실행 계층을 재사용한다. 작업 분할을 이유로 특정 호스팅 상품이나 분산 서비스 구조를 강제하지 않는다.

### 12.2 선행 묶음 A — 공통 계약과 통합 기반

첫 산출물은 저장소/기존 구현·의존성 현황, 실행 가능한 최소 개발 환경, 공통 데이터 계약, 동일 계산 예제다. 기존 코드가 있으면 새 구조를 덮어씌우지 않고 재사용/변경/누락을 대응표로 만든다.

공통 계약에는 아래를 포함한다.

| 경계 | 먼저 고정할 항목 | 변경 책임 |
| --- | --- | --- |
| 수치 | 금액/가격/지분 최소 단위, 반올림, EWMA 직렬화, 0/결측, 시간 단위 | 통합 담당+컨트랙트/데이터 검토 |
| 식별자 | market/record/position/epoch ID, 지갑/클러스터/프로그램 구분, query/formula/config 버전 | 통합 담당 |
| 관측→체인 | PublishedSnapshot 필드·해시·dataThrough·단조 버전·수용/거부 사유 | 데이터 생산, 컨트랙트 수용 |
| 체인→조회 | 계정/이벤트 형식, confirmed/finalized 단계, 재수집 커서·중복키 | 컨트랙트 생산, API 인덱서 소비 |
| 조회→화면 | Market/FreeRecord/Profile/Quote/Proof 응답과 오류 코드, 페이지네이션 | API 생산, 웹 소비 |
| 기록→증명 | finalized 이벤트, canonical manifest·hash·공통 근거 참조·대체 버전 | 체인/API 생산, 증명 워커 소비 |

계산 계약은 TypeScript 참조 모듈과 Rust 실행 모듈이 같은 입력/기대 결과를 대조하도록 한다. EWMA를 온체인에서 원자료 전체로 재계산한다고 가정하지 않는다. 커브·지급·예약·비용 등 양쪽에서 계산하는 항목의 정수 결과만 합의된 반올림과 일치시킨다. 단순히 같은 구현을 복사한 테스트에 의존하지 않고 보존 관계·경계·분할 거래를 별도로 검증한다.

초기 공통 예제: 정상 상승/하락, 상한 유지/이탈, 결측/실제0, 저활동, 졸업 대기/실행, 주간 경계, 무료 N/A, 증명 대기/오류다. 웹·API·워커가 같은 식별자/버전의 fixture를 사용한다. TTL·반올림처럼 관련 코드의 결과를 바꾸는 항목은 A 또는 해당 모듈 시작 시 구체 수치를 정하고 미해결 TODO를 정상 경로에 숨기지 않는다.

선행 연결 확인도 A에서 작게 진행한다: Seeker 지갑 서명, X 접근 범위/실제 쿼리 매칭, SAS의 Devnet 발급 경로, Arweave 번들 포함/20확인 검증 방법. 처음에는 adapter/fixture로 개발하되 실연결 미확인을 별도 표시한다. 유료 호출은 기존 예산과 실행 조건을 적용하며 이 계획 작성 자체로 호출하지 않는다.

### 12.4 병렬 진행과 담당 수

논리 묶음 7개가 동시 작업자 7명을 의미하지 않는다. 초기에는 아래 4개 작업 흐름이 현실적이다. 실제 배정은 아직 하지 않는다.

| 역할 | 묶는 작업 | 병렬 가능 범위 |
| --- | --- | --- |
| 통합/API 담당 | A→D, G 통합 책임 | 공통 계약 이후 인덱싱·API·운영 기반 진행 |
| 컨트랙트 담당 | B | 동일 회계 장부의 변경은 이 담당으로 모음 |
| 데이터/증명 담당 | C→E | C 기본 게시 경로 후 E 구현. 인원이 추가되면 C/E 분리 |
| 웹 담당 | F | fixture로 화면/지갑 개발 후 실제 API/IDL로 점진 연결 |

초기 A 계약을 맞추는 동안 웹 레이아웃·개별 외부 연결 확인·기존 코드 조사는 독립적으로 가능하다. A가 준비되면 B/C/D/F가 병렬 진행하며 E는 evidence 계약으로 모의 입력부터 시작할 수 있다. 온체인 계정/경제 계산과 공통 의존성 파일은 단일 변경 책임을 둔다. 하루 단위 일정은 기존 코드량·실제 인원·외부 접근 확인 전 추정하지 않는다.

### 12.6 병합/인터페이스 변경 방식

1. 한 작업은 하나의 소유 범위와 통합 가능한 작은 변경으로 만든다. 공통 타입/설정·의존성 lockfile·DB migration·IDL 생성은 통합 담당과 조율한다.
2. 공통 계약 변경이 필요하면 schema와 샘플/기대 결과를 먼저 갱신하고 영향을 받는 생산자/소비자를 명시한다. 기존 필드의 단위나 의미를 같은 버전에서 조용히 바꾸지 않는다.
3. 소비자는 버전 있는 fixture/adapter로 개발하고, 생산자가 합쳐지면 실제 경로로 교체한다. 실제 모드의 외부 오류를 fixture 성공으로 자동 대체하지 않는다.
4. 로컬 검증이 된 변경부터 기능 비활성 상태로라도 합친다. B의 계정 변경→IDL/생성 클라이언트→D/C/E/F 소비자 갱신→통합 흐름 시험의 의존 순서를 지킨다.
5. 매 통합본은 schema/formula/config·프로그램·클라이언트·DB migration 버전과 실행 환경을 함께 기록한다. 불일치하면 거래를 숨기거나 거절하고 자동 추정하지 않는다.
6. 병합 후 계약/필수 단위 검사와 해당 I단계 흐름을 통과해야 다음 범위를 개방한다. 공유 Devnet에서는 한 배포 담당이 프로그램/키/지갑 설정을 관리하고, 격리 시험에서 공용 데이터를 임의 초기화하지 않는다.
7. DB는 가능하면 추가→데이터 이행→소비자 전환 순서로 변경한다. 재배포/롤백 시 기존 on-chain 권리·미완료 청구·근거 참조를 지우지 않는다. 되돌리기 어려운 계정 레이아웃 변경은 버전 migration 명세를 먼저 둔다.

브랜치/PR/작업 디렉터리는 기존 저장소 규칙과 인원에 맞춰 생성할 구현 선택이다. 이번 계획에서는 생성·병합·원격 푸시하지 않았다. 머지 충돌이 없다는 것만으로 경제/데이터 계약이 맞는다고 판단하지 않는다.

### 12.7 작업 인계 양식과 남은 조건

각 묶음 인계에는 다음을 포함한다: 목적/범위, 소유 모듈·변경 파일, 입력/출력 schema 버전, 선행 묶음, fixtures, 실행/검증 명령, 통과 결과, 실제 외부 서비스 검증 여부, 필요한 설정 키의 이름(비밀 값 제외), 남은 제한, 영향받는 소비자. 스크린샷만으로 체인/회계/증명 기능 완료를 판정하지 않는다.

현재 외부 코드 작업공간은 HOME의 `external_workspace`이며 위치/현재 브랜치/기존 구현 범위 확인은 A의 첫 입력이다. 실제5개 키워드·키/계정·faucet 수치·홈서버 백업·외부 요금 실측은 실행 전에 필요하다. 이 값이 없어도 fixture 기반 공통/화면/계산 개발은 가능하다. 실제 서비스 연동 완료를 선언할 때는 해당 값/검증이 필요하다.

실행 계층 handoff 후보(아직 미발행): A 공통 계약/저장소 대응, B 온체인 단계 구현, C 수집·지표, D API/인덱서, E 보관·증명, F 모바일 웹, G 통합·배포 검증. 모두 `project_id=solana-colosseum`, 출처는 이 절, 기한 미정이다. 연결된 Hermes 실행 도구가 없어 작업 상태를 Markdown 체크박스로 관리하지 않으며, 실제 착수 시 이 명세를 참조해 Task를 발행/배정한다. 이 표와 인계 목록은 계획/후보이며 실행 중/완료 상태를 뜻하지 않는다.
