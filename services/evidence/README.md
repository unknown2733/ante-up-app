## Live validation update — 2026-10-12

The [live Arweave/SAS report](../../docs/implementation/ARWEAVE_SAS_VALIDATION.md) supersedes the older no-live-execution statements below. One actual X-backed free-chip result completed source storage (minimum22 confirmations), finalized Devnet SAS, protocol proof completion, indexer linking and independent HTTP/web-client readback. The separate N/A record and mobile UI remain unverified. `verify-devnet-proof.mjs` rechecks completion without signing/upload keys. `upload-journal.mjs` stages signed items before transport for response-loss recovery.

`scripts/prove-devnet.mjs` supplies `storageOptions.inclusionVerifier` from `inclusion.mjs`: it verifies parent signatures/data roots, bounded ANS-104 inclusion and item signatures without relying on absent gateway verification headers. `receipt.mjs` checks pinned service/version receipt signatures. `turbo.mjs` compresses large JSON losslessly and hashes the original canonical bytes. Claims use one Borsh string, matching the live `[12]` schema. The generic runtime accepts the same `storageOptions` through the CLI runtime module; a provider-header-only configuration does not gain independent inclusion verification automatically.

Current limitations and the receipt recovery incident are documented in the live report. No source/provider truth claim, local consensus-node verification, mainnet execution or public mobile UI validation is implied.

Run `npm test` from this directory, or `node --test services/evidence/*.test.mjs` from the repository root. Tests use fake transport/SDK injection plus the installed sas-lib encoder; they do not call Arweave or Solana.

`enqueue()` copies a finalized closed result into a durable JSON job. Every artifact carries exact UTF-8 content and a SHA-256 hash. `kind: 'market'` represents a reusable market common-evidence item; callers may pass its already known `ref` to avoid a new upload request. `processJob()` persists each upload reference. Once all refs exist, it canonicalizes a `ProofPayload` with sorted object keys, explicit null fields, UTF-8 bytes, and SHA-256. It then uploads those exact manifest bytes, preserving `manifestRef` separately. The manifest never contains its own locator/hash. Payload and result remain fixed across retries; storage status, retry metadata, and SAS ID are outside the hash.

The adapter must implement `upload(key, content, contentHash)`, `resolve(ref)`, `verify(ref, receipt)`, `fetch(ref)`, `lookupIssue(jobId, payloadHash, manifestRef, payload)`, and `issue(jobId, payloadHash, manifestRef, payload)`. `verify` must establish an allowed receipt signature/version, exact downloaded content, data-item inclusion in the stated parent transaction, and parent confirmations for **each** artifact **and the final manifest**. A 19-confirmation manifest blocks issuance even if artifacts have 20. `lookupIssue` reconciles an uncertain SAS submission before retry so the same job ID cannot be issued twice. The worker requires at least 20 confirmations for all refs and a finalized SAS result before `ISSUED`. The concrete Turbo adapter depends on an injected cryptographic receipt verifier and a gateway inclusion assertion; no live validation has been performed. The 20-confirmation threshold is an Ante Up policy, not a platform guarantee. [Turbo receipts](https://docs.ar.io/build/upload/receipts/), [Solana Attestations](https://solana.com/docs/tools/attestations).

The file repository uses atomic replacement for one local writer. `getProofStatus(repo, proofId)` is D's local read adapter boundary and returns `null` for an unknown ID. It does not infer proofId from recordId. `fetchManifest(adapter, status)` can recover the hashed manifest from `manifestRef` without the job file. Ordinary confirmation polling waits 300 seconds with no error or failure-count increase. Actual failures retry after 5, 15, then 60 minutes. An uncertain SAS submission is journaled before send; restart first reconciles its deterministic PDA and does not automatically send another transaction. Before deployment, add a cross-process lease or transactional DB, authorization for invalid/replaced proof transitions, queue budget limits, and 24-hour storage-pressure admission gating. A receipt alone must never be reported as completed storage or proof.

## Pinned SDK adapters

`@ardrive/turbo-sdk@2.1.0` and `sas-lib@1.0.10` were checked against npm registry and pinned in this module's lockfile. `turbo.mjs` calls the SDK's authenticated `upload` method only when explicitly given a configured client. It preserves the returned receipt in the job, separately resolves the ANS-104 parent via `/raw/<itemId>`, verifies exact bytes, checks gateway verification and root transaction headers, and reads the parent's `number_of_confirmations` through Arweave's transaction status endpoint. Upload acceptance alone leaves the job queued. The adapter **requires** a version-specific cryptographic `receiptVerifier` callback and fails closed without one. A gateway verification header is a provider claim; independent ANS-104 byte-range proof remains a deployment gate. [Turbo SDK](https://docs.ar.io/sdks/turbo-sdk), [receipt rules](https://docs.ar.io/build/upload/receipts/), [gateway headers](https://docs.ar.io/build/run-a-gateway/manage/verification-headers), [Arweave status](https://docs.arweave.org/developers/arweave-node-server/http-api).

The [receipt documentation](https://docs.ar.io/build/upload/receipts/) explicitly requires version-specific signature rules and says not to assume a high-level SDK verifier. The pinned Turbo SDK exposes upload receipts but no documented verifier for them. The callback must pin trusted service keys and receipt versions; it is a deployment trust boundary, not an optional boolean switch. [Wayfinder's separate verification strategies](https://docs.ar.io/sdks/wayfinder/wayfinder-core/verification-strategies/) describe client-side ANS-104 signature checking, but this module has not integrated an independent bundle inclusion proof.

`sas.mjs` uses `sas-lib` to derive a deterministic attestation PDA, construct the create instruction, and fetch a finalized, program-owned attestation account. Its issuer **always** re-fetches the archived manifest and runs `verifySemanticPacket` before lookup or issuance: finalized record, referenced finalized published snapshots, candidate payload/query/formula hashes, replayed observations, and entry/exit `h` must agree. `runtime.mjs` constructs the packet from `FileCandidateRepository` and D's finalized record/snapshot projection, normalizing only later `proofId` enrichment so the originally frozen manifest remains valid. It provides a stable SHA-256-derived nonce and canonical JSON claims codec; the registered SAS schema must match that byte layout. `kit.mjs` uses B's Kit runtime to submit SAS and generated `completeProof` instructions, and reads the finalized B record with owner/PDA checks. The completion journal reconciles the on-chain `proofComplete/proofHash` after restart; a different hash is rejected. No Devnet transaction was sent. [SAS create instruction](https://solana.com/docs/tools/attestations/instructions/create-attestation).

The semantic packet must be backed by archived `ProofPayload.evidence` refs. `calculationArtifact(recordId, points)` creates canonical JSON bytes with `{kind:"calculation",schemaVersion:"0.1",recordId,points:{entry:{published,replayInput},exit:{published,replayInput}}}`. `rawCountsArtifact(raw)` creates `{kind:"x-counts-raw",schemaVersion:"0.1",rawHash:SHA256(canonical(raw)),raw}`. The issuer downloads every ref, checks its byte hash and canonical encoding, requires exactly one calculation artifact identical to the packet, and requires an archived raw artifact for every `Observation.rawHash` in both replay inputs. Unrelated artifacts cannot satisfy these links. It does not independently infer observations from X raw responses; the finalized publisher and injected chain verifier remain responsible for that interpretation and provenance.

A finalized `CLOSED_NA` record may have no entry or exit snapshot. For that case `createKitMarketVersionReader()` checks B's finalized Market and Config owners/PDAs and supplies `queryHash`, `queryVersion`, `configVersion`, and formula version. The runner archives those values in a canonical `market-version` artifact, and the issuer compares them to a fresh finalized read. It does not invent version 1. If versions change before issuance, this route fails closed until a historical finalized version source is available.

`node cli.mjs` fails with `LIVE_EVIDENCE_DISABLED`. The explicit `--execute` path requires `.env.example` paths and an ignored runtime module. That module supplies `endpoint`, `programId`, `scope`, D's `SqliteProjectionStore` as `projection`, Turbo private key, `verifyTurboReceipt`, SAS credential/schema, Kit `payer`, `authority`, `proofAuthority`, and an explicit future Unix `attestationExpiry`. The CLI joins the projection with `FileCandidateRepository`, `FileRawResponseRepository`, and `FileJobRepository`, then creates Kit transports/senders. Set `ANTE_UP_RECORD_ID` to enqueue a finalized closed record or `ANTE_UP_PROOF_ID` to resume a job. No key or runtime module is provided here. The expiry is frozen in the job at enqueue; there is no one-day default or unsupported assumption that zero means never expiring. [Solana SAS expiry rules](https://solana.com/docs/tools/attestations/instructions/create-attestation).

`runtime.example.mjs` shows the ignored worker module shape. `ANTE_UP_INDEXER_MODULE` points to D's `src/sqlite.ts` under Node 24, `ANTE_UP_INDEX_DB` to its persistent SQLite file, and `ANTE_UP_SIGNER_MODULE` to an ignored module exporting the authorized signers and receipt verifier. `services/data/publisher.runtime.example.mjs` uses the same projection and `ANTE_UP_RPC_URL` for snapshot publication. Both examples fail immediately without their explicit environment and signer inputs.

`FileJobRepository` stores `{[proofId]: job}`. The job contains frozen `record`, `versions`, artifact UTF-8 content/hash/ref/receipt, `payload`, `payloadHash`, `manifestRef`, SAS submission journal, and `{completion:{state,signature}}`. D should use `getProofStatus(repo,proofId)` and `fetchManifest(storage,status)` for public proof reads. `ISSUED` means finalized SAS; `completion.state === "FINALIZED"` means B's proof hash also matches on chain. The two states must not be conflated.
# Automatic proof intake and funded admission — 2026-10-16

Live Devnet intake can discover every finalized closed result after the
existing backlog is reconciled. The program's cumulative cap permits only
proof obligations covered by the operator's reserved Turbo/storage budget.
`scripts/raise-funded-admission.mjs <cap>` is read-only by default; its
`--execute` path requires automatic intake, budget headroom, the protocol
admin signer and a durable transaction journal. A completed chip never
restores a spent admission. Existing accepted records remain proof duties
even when the admission gate or funded cap blocks new entries.
